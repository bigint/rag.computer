Base path: `/v1/auth/preferences` — Session-only.

A JSON scratch-pad scoped to the logged-in user. The admin UI uses it to persist sidebar state, default collection filter, preferred search mode, and similar client-side prefs. The server only interprets documented sensitive paths so it can encrypt and redact secrets.

## Get Preferences

```
GET /v1/auth/preferences
```

**Response** `200`:

```json
{
  "data": {
    "sidebar_collapsed": false,
    "default_collection": "knowledge_base",
    "chat": { "search_mode": "hybrid", "top_k": 10 }
  }
}
```

New users return `{"data": {}}`.

## Check Chat Credential Readiness

```
GET /v1/auth/preferences/chat-readiness
```

Session-only. Computes local credential eligibility for the authenticated user's browser chat and question-generation requests, which use OpenAI with the instance's default chat destination and no request credential or URL override. Accepts no user ID, key, provider or destination override. API-key and MCP-key authentication receive `403`; missing session authentication receives `401`.

**Response** `200`, with `Cache-Control: private, no-store`:

```json
{
  "credential_ready": true,
  "credential_source": "instance",
  "reason": null
}
```

`credential_source` is `saved`, `instance`, or `null`. Ready responses always have a source and a null reason. Blocked configuration returns `credential_ready: false`, a null source, and one of `missing_credentials`, `credential_blocked`, or `decryption_unavailable`. Unexpected database or runtime failures remain operational errors.

Saved credentials take precedence. An unbound, forged or mismatched saved key blocks instance fallback and must be saved again. Missing decryption configuration remains blocked; the existing invalid-ciphertext handling can discard a saved key and select eligible instance credentials. Editable `chat.has_openai_key` is presentation data and cannot establish readiness. The result is computed separately from writable preference `data` and contains no secret or destination.

This check performs no DNS, provider, retrieval or collection access request. It does not establish provider acceptance, connectivity, model availability or chat authorization, and does not describe arbitrary SDK credential/provider/URL overrides. Actual chat requests retain their existing checks and can reject a stale positive result.

Studio refreshes readiness on chat entry, focus, reconnect, every minute while foregrounded, after a personal-key save or clear, and after a current-session chat or question-generation error. Use **Check again** for a manual refresh. Sending and question generation wait for readiness and key changes to settle; personal-key controls, history and Stop remain available. Confirmed account changes cancel owned requests and discard late callbacks; cancellation cannot undo work the server has already accepted.

## Update Preferences

```
PUT /v1/auth/preferences
```

Deep-merges the request body into the stored preferences. Keys not present in the request are preserved. Ordinary keys sent as `null` are stored as `null`; documented sensitive paths such as `chat.openai_key` are cleared when sent as `null`.

```json
{ "data": { "default_collection": "knowledge_base" } }
```

The body may be either `{"data": {...}}` or a bare object — both are accepted.

**Response** `200`: echoes the merged public `data`.

Sensitive paths such as `chat.openai_key` are Fernet-encrypted at rest when `BIGRAG_MASTER_KEY` is configured. Preference responses do not return the key; they return `chat.has_openai_key` instead.

Saving `chat.openai_key` verifies it against the current instance chat provider and records its normalized destination with an authenticated signature derived from that key. The server owns this binding: incoming `chat.openai_key_base_url` and `chat.openai_key_base_url_signature` values are ignored, ordinary preference updates preserve the existing binding, and clearing the key removes both fields. Neither the binding nor the key is returned in preference responses. After changing `chat_base_url`, save a key for that endpoint again. Keys saved before authenticated destination binding was introduced also require saving again.

<Callout type="info">
  There is no size validation beyond the standard request-body limit, but keep payloads small (&lt;64 KB) — this isn't a document store.
</Callout>
