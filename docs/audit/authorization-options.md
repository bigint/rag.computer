# Replay authorization and tenant isolation options

Source baseline: `eb9486f9eeeab1e2e3f828cf385126b241f79b3b`, reviewed locally on 2026-10-04. These are proposed designs; this batch does not implement them, provision tenants, change schemas, or reindex data. Journal remains with its separate coordinator.

## Replay authorization

Reachability: with Redis available, a non-auth mutation carrying an Idempotency-Key and a cacheable body can return a saved successful response before the router runs. Both the direct cache hit and the failed-lock-acquisition fallback call `_send_cached` without executing dependencies or handler guards (`api/bigrag/middleware/idempotency.py`). A retained token/key value can still address that cache after logout, expiry, key revocation, role demotion, or scope changes. CSRF and maintenance middleware run outside replay, but do not establish current resource authorization.

`middleware/principal.py` chooses bearer before cookie. The uncached database auth path tries a session cookie before bearer, but the principal-cache path can choose a warm bearer entry when a valid cookie has no cache entry. Canonical selection must resolve that inconsistency explicitly. Auth principal caches also cannot be the sole fresh-revocation check. Route-specific gates include admin-session-only dependencies, collection pins supplied in JSON bodies, tenant filters, document ownership, and upload-session ownership. A successful login check alone is insufficient.

| Option | Minimal safe behavior | Compatibility and scope |
|---|---|---|
| R1: quarantine saved responses first | Return a generic conflict for completed cached requests instead of returning the saved body or running the handler again. Retain completion markers for their existing TTL. Apply the same generic conflict to every completed record in both replay branches, including mismatched-body, one-time, and legacy entries; preserve the remaining TTL and existing cache identity. Keep fresh requests on their existing authorization path. | Smallest immediate containment; authenticated retries that previously recovered a success now require operation-specific reconciliation. This blocks disclosure through replay but does not provide authenticated replay or solve the lease/body limits. |
| R2: shared read-only authorization before replay | Extract canonical credential selection and fresh database validation, then reuse endpoint read-only guards before either replay branch. Default to denial for routes lacking a complete guard. Only return a stored response after current admin/session, scope, collection/body, tenant, and ownership checks pass. | Preserves recovery for supported endpoints but requires coordinated auth/router changes and a complete route inventory. No database schema is inherently required. More reads occur on replay. Removed/changed resources can make a previously successful mutation unreplayable. |

Recommendation: R1 as a separately approved containment step, followed by R2 incrementally. R1 is a policy change, not a claim that finding 2 is fully fixed. Rejecting a cache hit must never evict its record and execute the mutation again. R2 should use one canonical selected credential: fresh-valid cookie first, then bearer when no valid cookie exists. This deliberately fixes the warm-bearer/cold-valid-cookie case rather than claiming all current cache paths already follow that rule. Under R2, validate the selected credential and current authorization before exposing cached bodies or cache-specific outcomes. R1 deliberately refuses all completed replay with one generic conflict; it is containment pending those shared guards.

Migration constraints for R2:

- Extract a database-read-only lookup; the existing `_user_from_api_key` also touches `last_used_at`, so calling it unchanged is not a read-only guard. Keep observability/cache updates separate from replay authorization.
- Preserve credential-scoped request identity rather than sharing cache entries across a user's keys/sessions. Unify identity selection only with compatibility handling for existing bearer-first cache keys; switching namespaces and treating old completions as fresh requests can repeat mutations.
- Inventory CSRF alongside canonical selection: current CSRF skips cookie checks for a Bearer header before knowing which credential auth selects. A shared trusted selected auth method, or equivalent fail-closed transport policy, must keep session CSRF checks consistent with cookie-first selection (`middleware/csrf.py`).
- Include explicit cache/guard versioning. Unsupported legacy completions remain tombstones/conflicts until expiry; do not discard them to make the retry succeed. Authorization denial returns the normal denial and never reaches a mutation handler.
- Separate authorization from mutable existence checks where a completed DELETE removed its own target. A route must define enough saved identity/authorization evidence to check its current boundary; missing evidence fails closed.
- Keep sensitive one-time responses unreplayable. Multipart/large-body bypass, Redis unavailability, and the 60-second unrenewed in-flight lease remain separate reliability limits (finding 18). Lease ownership/renewal and safe compare-and-delete need their own coordinated change.

Required mocked acceptance checks: expired/revoked session/key, demoted admin, reduced scopes, changed pin/tenant, wrong upload owner, warm-bearer/cold-valid-cookie, stale cookie cache, invalid-cookie/valid-bearer fallback, both cache branches, legacy entries, deleted targets, missing guard, and mismatched request bodies. Every denied replay must produce zero mutation/provider/vector writes.

Decision needed: choose R1 containment first or approve the R2 shared-guard extraction directly, and accept conflicts for legacy/unsupported recovery cases. No replay implementation proceeds before that choice.

## Tenant isolation

Current reachability is broader than tenant-key provisioning. Ordinary API-key create/update models do not expose `permissions.tenant`; tenant principals mainly depend on preexisting permissions. Collection creation already accepts `tenant_field`, and non-tenant-scoped callers can reach several operations on those collections:

- Suggestions check the collection pin but sample ready documents across the collection and store one suggestion row per collection (`services/chat/questions/api.py`, `db/models/document.py`). Collection analytics also aggregates without a tenant boundary (`routers/analytics.py`, `db/models/observability.py`). GET suggestion retrieval and analytics are unaffected by replay containment. POST suggestion generation also samples across the collection and sends those samples to the configured model before saving collection-wide questions.
- Vector upsert already forces tenant metadata; the gap is storage identity/overwrite ownership. `_point_id` uses collection and public ID only, so metadata stamping alone cannot prevent another tenant's existing ID from being replaced. Vector delete uses IDs without tenant filters (`routers/vectors.py`, `services/vector_store/base.py`). Truncate is collection-wide and lacks a tenant gate (`routers/collections/update_delete.py`).
- Upload sessions are checked against collection and issuing user, not issuing key/tenant (`services/upload_sessions.py`). Keys belonging to the same user are not separate tenant owners.
- Document ingestion builds chunk metadata from offsets/elements without document metadata (`services/queue_embedding/chunk_metadata.py`). Existing vectors can therefore lack the tenant field even when document metadata has it. Backfilling relational metadata alone does not repair vectors.

These are source-level reachability findings, not proof of live tenant data exposure. No live database, provider, vector, credential, or exploitation call was used. Standard API-key tenant assignment remains unavailable and is not added here. Tenant-marked collection creation is already reachable; a containment policy must gate it explicitly rather than assume all provisioning is currently disabled.

| Option | Minimal safe behavior | Compatibility and persistence decisions |
|---|---|---|
| T0: quarantine tenant-marked collections | Deny non-global-admin access to tenant-marked collections across reads, writes, body-selected collections, suggestions, analytics, uploads, vector mutation, and destructive operations. Include collection list/details/stats and global status/usage/timelines: filter only with verified attribution or deny mixed/unattributable aggregates. Gate tenant-marked collection creation before vector provisioning to fresh global session admins; do not add tenant-key assignment. | No schema/reindex required. Existing tenant keys and member sessions lose access to these collections until a supported model is ready. This is containment, not multi-tenant support. Direct ordinary-collection operations stay unchanged, but global summaries may change or become unavailable. The organizational admin exception requires a fresh current session/role check, not a cached admin role. |
| T1: shared collection with enforced tenant identity | Carry trusted tenant identity through every read/write, queue job, cache, vector storage ID, and ownership check. Propagate document metadata to chunks without overriding reserved fields; reject tenant-field names that collide with reserved payload identity/content fields. Tenant-safe overwrite/delete must be atomic or use tenant-qualified identity; lookup-before-write alone is unsafe. | Requires decisions about API-key tenant assignment, session behavior, global-admin exceptions, upload ownership, per-tenant suggestions/analytics, and legacy rows/vectors. Existing permissions JSON can represent a key tenant without a new key column; durable ownership, suggestion keys, and analytics attribution may require schema changes. Existing vectors require controlled backfill/reindex before enabling reads. |
| T2: separate collection/namespace per tenant | Operators allocate separate collections and pin each tenant's keys. Tenant access uses pinned keys; sessions must be restricted to approved global staff or receive an explicitly designed tenant mapping. Audit every global/body/document/queue/cache path to honor those boundaries before advertising isolation. Avoid shared raw-vector IDs, suggestions, analytics, and upload-session collections. | Simplifies storage boundaries and can use existing models for operator-managed allocation. Shared collections need an approved split/migration/reindex plan; tenant registry/self-service would be a separate schema/product decision. Existing collection names/keys change during migration. Member sessions and unpinned keys currently have no tenant mapping, so their access policy is an explicit compatibility decision. |

A route-only T0 gate would still be bypassed by existing completed-response replay. Apply R1 with T0, or implement trusted collection/global-admin authorization before both replay branches with path/body/document target resolution. Do not approve T0 as a handler-only fix.

Existing document reads and upload dedup already apply some pin/tenant checks (`services/documents/queries.py`, `services/documents/tenant.py`); the gaps above must be repaired around those existing checks, not by replacing them with a weaker generic login guard.

Recommendation: choose T0 for immediate containment if tenant-marked collections are not intended for current member/key use. For supported tenancy, prefer T2 when per-tenant collections are acceptable; otherwise T1 requires a larger coordinated design with the existing migration work. R1 does not protect these normal tenant routes.

Approvals required before persistence work: choose shared versus separate collection layout; define session/global-admin access and key-versus-tenant upload ownership; approve any columns/composite keys, legacy-row attribution, vector identity rewrite, and reindex/split strategy. Ambiguous legacy data must remain inaccessible to tenant callers until attribution is verified. Do not enable tenant API provisioning as a standalone patch.

Decision needed: approve T0 containment now or preserve current access while designing T1/T2; then select the durable layout. No tenant gate, provisioning, schema, or reindex implementation is included in this batch.
